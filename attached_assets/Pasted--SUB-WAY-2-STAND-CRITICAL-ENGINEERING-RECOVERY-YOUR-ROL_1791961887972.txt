## PHASE 1 — REAL RAILWAY GEOMETRY

This is the highest-priority technical task.

Find actual geospatial railway track alignment data for Seoul subway lines.

Investigate:

- OpenStreetMap railway ways
- OpenRailwayMap
- Official Korean railway GIS datasets
- Public railway infrastructure data
- Other legally reusable geospatial datasets

Download and preprocess the best available track centerline data.

Requirements:

1. Identify real track centerlines rather than schematic subway maps.
2. Convert latitude and longitude into a metric projected coordinate system.
3. Reconstruct ordered track segments.
4. Calculate signed curvature from local track geometry.
5. Detect curve entry, curve exit, and curve direction.
6. Estimate curvature uncertainty caused by sampling and map accuracy.
7. Associate track segments with subway lines and station order.
8. Preserve data provenance and licensing information.

**Do not derive railway curvature from straight lines connecting stations.**

Prioritize getting one actual segment working correctly, then expand to other available lines using the same processing pipeline.

Do not stop after finding URLs. Download the data, parse it, inspect it, and connect it to the application.

## PHASE 2 — TRAIN LOCALIZATION AND VELOCITY ESTIMATION

Use the existing Seoul real-time subway API.

Inputs may include:

- Train identifier
- Subway line
- Travel direction
- Last confirmed station
- Arrival/departure state
- Observation timestamp
- Historical travel time
- Track distance

The API does not directly expose exact train coordinates or instantaneous velocity.

Therefore implement a bounded train-state estimator.

Use physically plausible acceleration, cruising, braking, and station dwell models.

Estimate:

- Current track-distance interval
- Current velocity interval
- Likely operating state
- Position uncertainty
- Time until upcoming track features

Do not hardcode one fixed train speed and present it as real.

Use an appropriate probabilistic estimator if it materially improves performance, but avoid unnecessary mathematical complexity.

**A simpler calibrated model is better than an unvalidated complex filter.**

## PHASE 3 — SMARTPHONE SENSOR INTEGRATION

Implement actual smartphone motion sensing using Expo-supported APIs.

Use:

- Accelerometer
- Gyroscope
- Device orientation where available

Implement basic gravity compensation, filtering, and sensor-quality assessment.

Create a train-motion state detector capable of identifying candidate:

- Moving
- Decelerating
- Stationary
- Accelerating

Account for the fact that users may hold, rotate, or move their phones.

Do not assume that phone acceleration equals train acceleration.

Use confidence thresholds and hysteresis to avoid rapid false state transitions.

When an unexpected stop is detected with sufficient confidence:

- Suspend the existing curve-entry countdown.
- Stop pending voice alerts.
- Mark train location and speed estimates as uncertain.
- Resume prediction only after sufficient evidence of renewed motion.

Distinguish detecting an ongoing stop from predicting it in advance.

## PHASE 4 — PHYSICS-BASED MOTION FORECASTING

Connect the following pipeline:

**Live Train State + Real Track Centerline + Sensor Observations → State Estimation → Physics Engine → Upcoming Motion Forecast → Voice Alert**

Calculate:

- Signed track curvature
- Lateral acceleration
- Longitudinal acceleration
- Lateral jerk
- Curve-entry time window
- Direction of passenger sway
- Prediction uncertainty

Include cant compensation only when actual or justified cant data exists.

Do not invent train suspension parameters, vehicle masses, or precise rail irregularity profiles.

Vehicle-specific dynamics should be modular and optional.

Implement physically consistent sign conventions and unit tests.

For unknown parameters, propagate uncertainty instead of silently assigning precise values.
